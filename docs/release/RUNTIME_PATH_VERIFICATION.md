# Runtime path verification gate

## Purpose

Remote staging and production workflows must not write to a server until an
operator has collected and reviewed a read-only runtime contract for that exact
host and those exact paths.

The runtime contract is generated by
`.github/workflows/runtime-path-inventory.yml`. It sends
`scripts/runtime-path-inventory.sh` over an SSH session through standard input;
the script is not installed on the host and does not create, update, delete,
restart, pull or deploy anything.

## Workflow availability

GitHub accepts `workflow_dispatch` only when the workflow file exists on the
repository's default branch. The default branch is currently `main`; this PR
does not change it. Before runtime inventory is attempted, merge the reviewed
workflow and its script into the approved default control-plane lineage, or
adopt another reviewed GitHub-supported dispatch arrangement. Do not copy the
workflow ad hoc onto `main`, and do not change the default branch merely to
bypass review.

## Required GitHub environments

Create these environments separately:

- `staging-runtime-audit`
- `production-runtime-audit`
- `staging`
- `production`
- `release-governance`

The two audit environments should use a non-root SSH account. The account needs
only enough directory traversal and metadata access to inspect the declared
runtime root, the non-secret environment file and the presence of required
secret files. Docker access is optional and is reported only as an observation.

Each audit environment uses:

- `RUNTIME_AUDIT_HOST`
- `RUNTIME_AUDIT_USER`
- `RUNTIME_AUDIT_SSH_KEY`
- `RUNTIME_AUDIT_KNOWN_HOSTS`
- optional variable `RUNTIME_AUDIT_SSH_PORT`

`RUNTIME_AUDIT_KNOWN_HOSTS` must be copied from a trusted out-of-band source.
The workflows deliberately never run `ssh-keyscan`.

## Read-only inventory procedure

1. Confirm the reviewed workflow exists in the approved default control-plane
   lineage.
2. Open **Actions → Runtime path inventory (read only)**.
3. Select `staging` or `production`.
4. Enter the proposed existing runtime root, externally managed environment
   file, secrets directory and loopback API port.
5. Run the workflow.
6. Download and review the `runtime-path-contract-*` artifact.
7. Confirm:
   - the machine fingerprint is the expected host;
   - every canonical path matches the approved runtime layout;
   - no declared path is a symlink;
   - the runtime root and secrets root are directories;
   - the environment file is a regular file;
   - `ENABLE_EXTERNAL_DELIVERY=false`;
   - `ENABLE_REGISTRY_ENRICHMENT=false`;
   - required secret-file presence is complete;
   - `ready_for_write_disabled_deploy=true`;
   - `server_modified=false`.
8. Record the exact SHA-256 runtime fingerprint in the change record.

The fingerprint covers host identity, canonical paths, inode/ownership/mode
metadata, safety flags and hashes of known non-secret deployment files. Any
material path change makes the fingerprint stale.

## Deployment gate

A staging or production deployment requires the exact reviewed fingerprint as
an input. The workflow performs the same read-only inventory twice:

1. in the dedicated runtime-audit environment; and
2. again with the deployment identity immediately before the first remote
   write.

If either fingerprint differs, if the path is a symlink, if safety flags are
not explicitly false, or if required files are absent, the deployment stops
before upload, registry login, directory creation, container changes or
database changes.

## Deployment identities

The staging and production environments use separate deployment credentials
and pinned `known_hosts` data. They also use dedicated read-only GHCR tokens:

- staging: `STAGING_GHCR_USER`, `STAGING_GHCR_READ_TOKEN`
- production: `PRODUCTION_GHCR_USER`, `PRODUCTION_GHCR_READ_TOKEN`

The workflows log out of GHCR after the operation. Runtime environment and
secret files remain outside the release package; the workflows do not upload
or persist canary credentials.

## Reverification

Run a new inventory after any of the following:

- host rebuild or replacement;
- path, owner, group, mode or inode change;
- environment or secrets directory relocation;
- proxy or Compose file replacement;
- current-image identity change;
- unplanned operational drift.

A prior fingerprint must never be reused after drift.
